# MyUPNP 代码架构

本工程从零手写实现了一个 **DLNA/UPnP 控制点 App**（发现 → 描述 → 控制 → 事件 → 播放 → 队列连播），
外加一个 Python 虚拟音响设备端（B1）。本文说明各文件职责与依赖，方便后续扩展。

> 更新记录：第 7 课 B（播放队列/连播，提交 `a5aeba2`、`f7033d8`）后整体修订。

---

## 1. 总览：模块职责划分

```
 MainActivity（UI 编排层：权限/网络回调/对话框/列表/控制条/队列入口）
        │  collect 渲染
        ▼
 MainViewModel（UI 状态单一来源 + 后台编排）
   │  持有并注入线程池/Handler：
   ├── DeviceRegistry         设备注册表：增删/心跳超时/描述拉取/分组
   ├── SubscriptionManager    GENA 订阅生命周期：订/续/退、SID 反查
   ├── NowPlayingSession      播放会话：钉住"设备+服务+曲目"，播完判定
   └── PlaybackQueue          播放队列：待播 / 当前 / 已播历史（纯逻辑）
        │  网络全部丢后台（controlExecutor / fetchExecutor / 引擎自有线程）
        ▼
 协议包（无 UI、可独立复用/单测）
   ssdp/ 发现 · soap/ SOAP · gena/ 事件 · dlna/ DLNA 编排 · device/ 描述与 SCPD
```

**分层原则**：
- 协议包（`ssdp/ soap/ gena/ dlna/ device/`）只做协议，不依赖 Activity。
- 状态类（`DeviceRegistry / SubscriptionManager / NowPlayingSession / PlaybackQueue`）
  持有逻辑与状态，通过 **Listener 接口** 通知 UI，自身不碰 View。
- `MainViewModel` 是**唯一编排中枢**：线程池、Handler、扫描子系统、事件服务器、
  队列记账与自动连播都在这里；Activity 只引用（不 new Executor）。
- `MainActivity` 只做 UI 编排：对话框、转发用户操作、把 StateFlow 画到界面。
- `model/` 放纯数据模型（无逻辑）。

## 3. 关键设计约定（扩展前必读）

### 3.1 线程模型（全 App 一致）
- **网络 IO 一律不进主线程**：引擎在自有线程；HTTP/SOAP/订阅放 `controlExecutor`；
  描述拉取放 `fetchExecutor`。
- **回调回主线程**：后台完成后用 `mainHandler.post { ... }` 再碰 UI/共享状态。
- **队列记账只在主线程**：`queueEnqueue / queue* / commit* / autoAdvanceQueue` 都从
  主线程调用（UI 点击、事件回调、onTrackEnded 均在主线程）；推送上 `controlExecutor`，
  成功后 `mainHandler.post` 里才 `commit*` —— 失败不改队列，播不了的歌不会被吞掉。
- **网络回调（ConnectivityManager.NetworkCallback）在系统线程**，一律 post 到主线程再处理。

### 3.2 状态类的事件回调（以 NowPlayingSession 为例）
```kotlin
val nowSession = NowPlayingSession(mainHandler, controlExecutor, listener = object : ... {
    override fun onChanged(session) { syncNowPlayingState() }        // 状态变化 → UI
    override fun onTrackEnded(session) { autoAdvanceQueue() }        // 一首自然播完 → 连播
})
```
扩展新功能时：**别让状态类直接持有 Activity/View**，加 Listener 方法即可。

### 3.3 两条用户操作的完整流动

**a) 曲库点歌（常驻浏览器可连续操作）**
```
进曲库 → MainActivity.showMediaBrowser(cds)：一个常驻对话框（ListView + 返回上级/关闭）
   ├─ 点文件夹 → objectId 入栈 → reload() 重新 Browse（对话框不关）
   └─ 点歌曲 → mediaItemOptions(item) 弹菜单：
        ├─ "立即播放"   → playMediaItemFromServer(item)：收集播放器→弹选择框(可刷新)
        │                   → pushToRenderer → DlnaPlayer.pushAndPlay（后台）
        │                   → 成功 → nowSession.begin(...) 控制条出现
        │                          → vm.queueOnPlayed(item) 记成队列"当前"
        │                          → vm.activateDeviceSubscription(...)
        └─ "加入队列"   → vm.queueEnqueue(item)：只入队，不打断；浏览器仍开着可继续加
```

**b) 自动连播 / 上一首 / 下一首**
```
一首自然播完 ──▶ NowPlayingSession 判定（见 3.4）──▶ Listener.onTrackEnded
                ──▶ MainViewModel.autoAdvanceQueue()
                      playbackQueue.nextUp 预览队首
                        → pushQueueItem(item)（推给当前会话钉住的播放器，后台）
                          → 成功: commitNext(item) 记账 + nowSession.begin(新标题)
                                  + toast "正在播放"
                          → 失败: 队列不动，toast 原因
控制条"下一首" → vm.queueNextItem()          （同 autoAdvanceQueue 的推送逻辑）
控制条"上一首" → vm.queuePreviousItem()      （回放 history 栈顶，当前曲放回队首待接）
首页/控制条"队列(N)" → showQueueDialog()：正在播 + 待播 N 首 + 已播计数
        ├─ 点待播一首 → playQueueRow(item,i)：
        │       有会话 → vm.queuePlayPendingAt(i) 直接切
        │       无会话 → 转 playMediaItemFromServer(item)（先选设备开播）
        └─ 清空队列   → vm.queueClear()
```

### 3.4 "一首播完"的判定（NowPlayingSession，双保险）
只认**自然播完**，手动停止不触发连播：

| 状态/字段 | 含义 |
|---|---|
| `lastWasPlaying` | 上一刻是否在播（PLAYING）。播完判定的前提 |
| `userStopRequested` | 用户手动 Stop（stop() 置位）；toggle Play / begin / end 复位 |
| `suppressEndUntilPlaying` | begin 声称"在播"后先等一次真实 PLAYING 事件，屏蔽设备旧 STOPPED 误判 |
| `endOverrunSec` | 本地兜底计数：超过片尾 (3s 余量 + 4s) 仍无停止事件 → 判定播完 |

判定来源两条路：
1. **GENA 事件**（`applyEvent`）：`lastWasPlaying && 新状态∈{STOPPED, NO_MEDIA_PRESENT}
   && !suppress && !userStopRequested` → `onTrackEnded`；
2. **本地兜底**（`tick`，播放时钟每秒推）：部分设备事件不可靠（见已知问题 #1），
   `durationSec > 10 && positionSec 超过片尾 3s` 持续 4s 仍无事件 → 同样判播完；
   `syncProgress` 把进度拉回片尾内时计数清零。

### 3.5 日志约定
- 界面不滚动日志（第 6 课后移除）。
- 排查统一走 logcat：`adb logcat -s MyUPNP`。
- 关键节点已按模块打 tag 前缀：
  `[SSDP] [DEVICE] [DESC] [CDS] [SOAP] [GENA] [NET] [NOW] [SCAN] [SUB] [EVENT] [QUEUE] [MEM]`。

## 4. 扩展指南（按功能列）

| 想加什么 | 动哪个文件 | 注意 |

`UiState`（StateFlow），Activity 用 `collect` 渲染，不要用 Activity 字段存业务状态。

### 4.1 收费功能接入（单包 + 运行时解锁）

设计原则：**业务代码只问 FeatureGate，不碰计费细节**。播放队列目前已实现但走
`EverythingFreeGate`（全免费）。将来若要把队列设为付费功能：

```kotlin
// 1) FeatureId.PLAYBACK_QUEUE 已登记（core/FeatureId.kt）
// 2) 写 SubscriptionFeatureGate : FeatureGate，内部查 Billing 购买状态
// 3) 在 MainViewModel 把 featureGate 换成新实现（只改一处）
// 4) 在入口拦截，例如 queueEnqueue / pushQueueItem 开头：
if (!vm.guardFeature(FeatureId.PLAYBACK_QUEUE) { msg -> vm.postMessage(msg); return }) {
    // ...真正入队/连播逻辑
}
```

注意：
- **不要**在业务代码里写死"if 买过 xxx"——一律经 `featureGate`。
- **不要**现在接 Billing SDK / 双 flavor，等商业决策定了再补；口子已留好。

## 6. 已知问题 / 待排查（Todo）

| # | 问题 | 现象 | 待查方向 / 现状 |
|---|---|---|---|
| 1 | **活动设备自动订阅不生效** | 播放/操作后自动订阅该设备全部服务，但其他控制点调进度/音量时仍未同步 | 检查 SUBSCRIBE 是否成功、SID 是否记录、事件服务器是否收到 NOTIFY（logcat `[SUB]`/`[GENA]`/`[EVENT]`）。可能设备对多订阅/同一回调地址有限制。**已缓解**：自动连播的"播完判定"配了本地兜底，不依赖事件也能推进队列 |
| 2 | 连播触发依赖 GENA + 本地兜底 | 若设备**完全不推事件且不报时长**（duration=0），兜底需 duration>10s 才生效，可能不自动下一首 | 方向：对不报时长的轨道加 GetPositionInfo 轮询探测"停止"；或推歌后主动 GetMediaInfo 补时长 |
| 3 | 本地兜底可能提前切歌 | 时长元数据不精确时（超片尾 3s+4s 仍无事件即判定）可能少播几秒 | 已留余量；真机若频繁误切可加长宽限或要求两次连续 STOPPED 再切 |
| 4 | 队列不跨重启 | App 重启后排队列表清空（有意为之的 v1） | 方向：仿 `playback_memory` 持久化 pending（见第 4 节扩展指南） |
